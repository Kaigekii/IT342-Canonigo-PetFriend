Phase 4 focused on creating cross-cutting concerns that apply to all features across the entire application. Instead of duplicating error handling, validation, or constants in each feature, we centralized these in the shared layer for consistency and maintainability.

## ✅ What Was Accomplished

### 1. Centralized Exception Handling Framework (1 file)
**File**: `GlobalExceptionHandler.java`

**Purpose**: Unified error handling for entire application

**Features**:
- Automatic exception catching and formatting
- Consistent error response structure
- Field validation error aggregation
- Proper HTTP status codes (400, 401, 403, 404, 500)
- Request context in error responses

**Handles**:
- `MethodArgumentNotValidException` → Validation errors (400)
- `ResourceNotFoundException` → Missing resources (404)
- `InvalidOperationException` → Bad operations (400)
- `UnauthorizedException` → Auth failures (401)
- `ForbiddenException` → Permission denied (403)
- Generic exceptions → Server errors (500)

**Error Response Format**:
```json
{
  "timestamp": "2026-05-09T10:30:00",
  "status": 400,
  "error": "Bad Request",
  "message": "Validation failed",
  "path": "/api/pets",
  "details": {
    "name": "Name is required",
    "species": "Invalid species"
  }
}
```

**Usage in Services**:
```java
if (pet == null) {
  throw new ResourceNotFoundException("Pet with ID " + id + " not found");
}

if (!booking.getOwnerId().equals(userId)) {
  throw new ForbiddenException("You don't have permission to modify this booking");
}

if (booking.getStatus().equals(CANCELLED)) {
  throw new InvalidOperationException("Cannot modify a cancelled booking");
}
```

#### InvalidOperationException
```java
throw new InvalidOperationException("Cannot cancel completed booking");
```

- HTTP 400
- Use when operation violates business logic
- Examples: modifying cancelled booking, invalid state transitions

#### UnauthorizedException
```java
throw new UnauthorizedException("User not authenticated");
```
- HTTP 401
- Use when user is not logged in
- Security checks should use this

#### ForbiddenException
```java

```
- HTTP 403
- Use when user lacks permission for resource
- Resource ownership checks should use this

## 📝 Usage Guide

### In a Feature Service

```java
@Service
public class SitterService {
  
  public SitterDto getSitterById(Long id) {
    // Use exception handling
    Sitter sitter = sitterRepository.findById(id)
      .orElseThrow(() -> new ResourceNotFoundException(
        "Sitter with ID " + id + " not found"
      ));
    return sitterMapper.toDto(sitter);
  }
  
  public void registerSitter(RegisterSitterRequest request) {
    // Use validation utilities
    if (!ValidationUtil.isValidEmail(request.getEmail())) {
      throw new InvalidOperationException(ValidationUtil.INVALID_EMAIL_MESSAGE);
    }
    
    if (!ValidationUtil.isValidPhone(request.getPhone())) {
      throw new InvalidOperationException(ValidationUtil.INVALID_PHONE_MESSAGE);
    }
    
    // Use constants
    Sitter sitter = new Sitter();
    sitter.setRole(AppConstants.ROLE_PET_SITTER);
    sitter.setVerificationStatus(AppConstants.VERIFICATION_STATUS_PENDING);
    // ...
  }
}
```

### In a Feature Controller

```java
@RestController
@RequestMapping(AppConstants.API_SITTERS)
public class SitterController {
  
  @GetMapping("/{id}")
  public ResponseEntity<ApiResponse<SitterDto>> getSitterById(@PathVariable Long id) {
    SitterDto sitter = sitterService.getSitterById(id);
    return ResponseEntity.ok(
      ApiResponse.success("Sitter retrieved successfully", sitter)
    );
  }
  
  @PostMapping
  public ResponseEntity<ApiResponse<SitterDto>> createSitter(@Valid @RequestBody RegisterSitterRequest request) {
    SitterDto sitter = sitterService.registerSitter(request);
    return ResponseEntity.status(HttpStatus.CREATED).body(
      ApiResponse.success("Sitter created successfully", sitter)
    );
  }
  
  // Exceptions automatically caught by GlobalExceptionHandler
  // No need to manually handle exceptions here
}
```
